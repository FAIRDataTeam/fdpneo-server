# Security Audit — FDP-neo (server + client)

**Date:** 2026-06-07 · **Context:** evaluation for a hospital (high-assurance) deployment —
HIPAA / GDPR, defense-in-depth · **Scope:** `fdp-server` and `fdp-client` repositories,
plus the running dev stack (GraphDB, Postgres, Keycloak) · **Reviewer:** security review
(static code review + live runtime verification).

## Methodology

1. **Static review** of authn/authz, input handling, secrets, transport, privacy, the
   `/users` IdP facade, and dependencies.
2. **Live verification** against the running server (`:8000`) with real `steward`
   (`alice`) and `admin` tokens and a loopback callback listener, to confirm or refute the
   static findings. Probes were benign (own listener, harmless targets, no data
   exfiltration); all test records were removed afterward.

Runtime testing **materially corrected** the static read: two parsing findings flagged as
High/Med-High did not reproduce, and one different parsing vector did. Verdicts below are
evidence-backed.

## Executive summary

The architecture has a **strong security core** — OIDC-only (no password store), sound JWT
validation, ODRL authorization with one-graph-per-record isolation, a **fail-closed**
SPARQL access-control rewriter, anonymized-by-design metrics, CSPRNG API keys, conditional
writes, and a least-privilege user-management facade. The material risks are concentrated
at the **deployment perimeter** (TLS, security headers, rate limiting) and in **one
confirmed input-parsing SSRF** (JSON-LD remote `@context`). None of the findings indicate a
broken authorization model.

**Go-live blockers:** the JSON-LD SSRF, TLS+HSTS, security headers, rate limiting, and a
triple-store conformance gate.

## Detailed findings

### F-01 — JSON-LD `@context` SSRF (Med-High, CONFIRMED)

A `steward`-authenticated `POST /catalog` with `Content-Type: application/ld+json` and a
remote `@context` URL caused the **server** (RDFLib's JSON-LD loader, `rdflib-7.6.0`) to
issue an outbound `GET` to an attacker-controlled **loopback** URL before validation failed
(`400`). The callback listener logged: `GET /jsonld-context-probe UA=rdflib-7.6.0`.

- **Impact:** any data steward can make the FDP server perform blind HTTP GETs to arbitrary
  internal/loopback addresses (internal admin endpoints, service ports, cloud metadata
  `169.254.169.254`). No allowlist; loopback not blocked. Blindness limits secret
  exfiltration but enables internal recon/port-scanning and hitting GET-actionable internal
  services — a real foothold on a segmented hospital network.
- **Location:** `src/fdp/metadata/ldp/negotiation.py:127` (`graph.parse(..., format="json-ld")`),
  reachable from the LDP write router (POST/PUT/PATCH).
- **Remediation (R-01 in the plan):** stop the JSON-LD parser from fetching remote
  documents — inject a no-network `document_loader`, or drop `application/ld+json` from the
  *write* parse path (keep it for read serialization). See the plan.

### F-02 — No rate limiting (Med-High, CONFIRMED)

A burst of 30× `GET /config` all returned `200` — no `429`, no throttling. Nothing limits
`/sparql`, `/search`, SHACL-on-write, `/labels`, or `/users` (which amplifies into
Keycloak). Enables resource-exhaustion DoS and IdP amplification.

- **Location:** no limiter middleware in `src/fdp/main.py`.
- **Remediation:** R-02.

### F-03 — Triple-store conformance is a security boundary (High, conditional)

Reads are authorized by projecting only the caller's authorized graphs via repeated
`named-graph-uri` parameters; the rewriter is correctly **fail-closed**
(`src/fdp/access/rewriter.py:105` — any explicitly named, unauthorized IRI → `403`; no
graphs named → project exactly the authorized set). Correctness is **delegated to the store
honoring that projection.** Oxigraph is documented to mishandle repeated `named-graph-uri`,
which on that backend could surface graphs outside the authorized set — i.e., **PHI leakage
across records/tenants.** There is no hard gate preventing `/sparql` on a non-conformant
store. The live deployment runs **GraphDB** (conformant), so this is not currently
triggered.

- **Remediation:** R-03 (startup conformance gate + supported-store policy).

### F-04 / F-05 — No TLS, no security headers (Med, CONFIRMED)

The live server speaks **plain HTTP** on `:8000` (no HTTPS listener) and returns no
security headers — only `server: uvicorn` (software-disclosure banner). Missing: HSTS, CSP,
`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`.

- **Remediation:** R-04 (TLS/HSTS at the edge) and R-05 (security-headers middleware).

### F-06 — Client token storage + no CSP (Med, client)

`client/src/auth/userManager.ts` sets no `userStore`, so `oidc-client-ts` persists tokens
in Web Storage (readable by any XSS); no CSP ships with the client. Partially mitigated by
Auth-Code + PKCE and a 300s access-token TTL; *positives:* no `v-html`/`innerHTML` sinks, no
implicit flow.

- **Remediation:** R-06.

### F-07 — Deployment hardening + committed dev secrets (Med, repo)

Only `deploy/compose.yaml` (dev) exists — no TLS/secret-management/network-policy manifests.
Committed dev artifacts that must never reach prod: `KEYCLOAK_ADMIN_PASSWORD: admin`, realm
user `admin/admin`, and `fdp-server-dev-secret` (added for the `/users` facade).

- **Remediation:** R-04 / R-09.

### F-08 – F-12 (Low / Info)

- **F-08:** `/users/{id}` interpolated into the Keycloak admin URL without a UUID check.
  Live: `/users/not-a-uuid-<script>` → `404` (handled; FastAPI single-segment routing blocks
  traversal). Defense-in-depth only. → R-07.
- **F-09:** several `log.*(subject=ctx.subject)` lines record the user identifier (PII under
  GDPR). No tokens/passwords/PHI/query-text are logged. → R-10.
- **F-10:** unexpected (non-`FDPError`) exceptions return a bare `500` without the structured
  envelope/CORS (no traceback leak; debug is off). → R-08.
- **F-11:** `/users` role changes are audited by Keycloak but not mirrored into the FDP
  `AuditLog`. → R-11.
- **F-12:** deps are locked (`uv.lock`, `package-lock.json`) but no SCA/SBOM scanning in CI.
  → R-12.

## Refuted findings (verified safe at runtime)

- **R-01 — RDF/XML XXE:** external DTD → **no callback**; `file:///etc/hostname` entity
  resolved to an empty title (`""`). RDFLib 7.6.0 neutralizes RDF/XML XXE. *Keep RDFLib
  pinned ≥7; add a regression test so a downgrade can't reintroduce it.*
- **R-02 — `LOAD` source SSRF:** the SPARQL update PEP is genuinely fail-closed — every
  `LOAD` was blocked (`403`), including into the steward's own freshly-created graph;
  target-less `LOAD` → `400`. Residual (defense-in-depth only): the `LOAD` *source* URL is
  never allowlisted, so a principal that *did* hold a modify-authorized target could SSRF.
  → R-03b.

## Positive controls verified

- **JWT:** asymmetric algorithms only (`RS*/ES*`), `aud/iss/exp/iat/sub` required,
  alg-confusion guarded (`identity/middleware.py:143-161`).
- **SPARQL PEP:** fail-closed projection; `SERVICE` federation rejected; anonymous and
  ambiguous-target updates rejected; `LOAD` blocked by per-graph authz (verified live).
- **Conditional writes enforced:** `DELETE`/`PUT` without `If-Match` → `428`; correct ETag →
  `204` (lost-update protection, verified live).
- **Metrics:** `subject` dropped unconditionally; IP → coarse geo; salted rotating visitor
  hash (`metrics/anonymize.py`) — strong GDPR posture.
- **API keys:** `secrets.token_urlsafe(32)` + `sha256` storage; secrets via `SecretStr`;
  `.env` gitignored; deps locked.
- **`/users` facade:** least-privilege service account, capability-gated, invite-only,
  self-lockout / last-admin guards, curated role set (verified live earlier).
- **RDFLib 7.6.0** safe against RDF/XML XXE.

# Remediation plan

Sequenced into three phases. Effort: **S** ≤ ½ day, **M** ~1–2 days, **L** > 2 days.
Each item lists the technical approach and an acceptance check.

## Phase A — go-live blockers

### R-01 · Eliminate the JSON-LD `@context` SSRF (F-01) — **S** — ✅ DONE (2026-06-07)
- **Implemented:** `metadata/ldp/negotiation.py` now rejects any *string*-valued
  `@context`/`@import` (the network-fetch vectors) anywhere in a JSON-LD write body, **before**
  `graph.parse` runs — inline (object) contexts still parse. Returns `400 fdp.bad_request`.
  No other JSON-LD parse sites exist in the codebase.
- **Verified:** unit tests (`tests/unit/metadata/ldp/test_negotiation.py`, incl. a
  monkeypatched `Graph.parse` proving the guard short-circuits before any parse); and a
  **live re-run of the F-01 probe** — the remote-`@context` POST now returns `400` and the
  callback listener received **no** request. SSRF closed.

### R-02 · Rate limiting + request quotas (F-02) — **M** — ✅ DONE (2026-06-07)
- **Implemented:** two dependency-free pure-ASGI middlewares in `shared/limits.py`,
  registered in `main.py` just inside CORS / outside auth (so floods and oversize bodies are
  shed before the JWKS/auth work): `RateLimitMiddleware` (per-IP fixed window → `429` +
  `Retry-After`) and `BodySizeLimitMiddleware` (`Content-Length` fast-path **and** streamed
  byte-count → `413`). Config group `RateLimitSettings` (`FDP_RATELIMIT_*`): defaults
  300 req / 60 s, 10 MiB body, `trust_forwarded_for=False`, `enabled=True`. The existing
  SPARQL HTTP read timeout is now configurable (`FDP_TRIPLESTORE_QUERY_TIMEOUT_SECONDS`,
  default 30) and maps timeouts to a clean `504 fdp.gateway_timeout` instead of a raw 500.
- **Verified:** unit tests (`tests/unit/shared/test_limits.py`,
  `tests/unit/storage/test_triplestore_adapter.py`); and **live** — a burst tripped `429`
  with `Retry-After: 60` at the configured limit, an 11 MiB POST returned `413` (before auth),
  and a small POST passed the cap to auth (`401`).
- **Remaining (ops):** the *authoritative* limiter is the reverse proxy/ingress (this is
  per-instance defense-in-depth); tune the limits per deployment and set `trust_forwarded_for`
  when behind a header-sanitizing proxy.

### R-03 · Triple-store conformance gate (F-03) — **M** — ✅ DONE (2026-06-07)
- **Implemented:** `storage/triplestore/conformance.py` runs a startup self-test
  (`verify_named_graph_isolation`) — writes three disjoint probe graphs, counts a projection
  over two of them via repeated `named-graph-uri`, and requires exactly `2` (the third and
  every other graph excluded; repeated params unioned). The lifespan
  (`_verify_store_conformance`) sets `app.state.sparql_multigraph_safe`; the SPARQL router
  (`build_sparql_router(multigraph_safe_provider=…)`) **fails closed** — a read whose
  authorized projection spans >1 named graph is refused `503` when the store is not safe
  (single-graph reads still allowed). Configurable via
  `FDP_TRIPLESTORE_VERIFY_NAMED_GRAPH_ISOLATION` (default true).
- **Verified:** unit tests (`tests/unit/storage/test_conformance.py`,
  `tests/unit/access/test_router.py` — multigraph→503 when unsafe, single-graph→200); and
  **live** — the self-test against the running GraphDB returns **CONFORMANT** (probe graphs
  cleaned up), a multi-graph `/sparql` read returns `200`, and an unsafe store would `503`.
- **Remaining (ops):** deploy only GraphDB/Fuseki for `/sparql`; treat a failed self-test in
  the boot logs as a release blocker.

### R-03b · Reject `LOAD` source (R-02 residual) — **S** — ✅ DONE (2026-06-07)
- **Implemented:** `access/parser.py` now rejects `LOAD` outright (`400`) — its source URL
  would be dereferenced by the store (SSRF), and only the *target* graph is authorized. Bulk
  import is a server-side operation, not a public-SPARQL one; internal write paths don't use
  `LOAD`.
- **Verified:** unit tests (`tests/unit/access/test_parser.py`); and **live** — `LOAD` via
  `/sparql` returns `400 fdp.bad_request` "LOAD is not permitted".

### R-04 · TLS + HSTS + hardened deployment (F-04, F-07) — **M/L**
- **Approach:** terminate TLS at an ingress/reverse proxy; enable HSTS
  (`max-age` ≥ 1 year, `includeSubDomains`, `preload`); HTTP→HTTPS redirect; set `base_url`
  to the HTTPS origin. Provide a production deployment artifact (helm/compose-prod) with:
  secrets via Vault/sealed-secrets (rotate every dev credential — `admin/admin`,
  `fdp-server-dev-secret`), network segmentation FDP↔store↔Postgres↔IdP, and
  encryption-at-rest for Postgres and the triple store.
- **Accept:** plain-HTTP is unreachable in prod; HSTS present; no dev secret in any non-dev
  config; secrets sourced from the secret manager.

### R-05 · Security-headers middleware (F-05) — **S** — ✅ DONE (2026-06-07)
- **Implemented:** `shared/security_headers.py` (`SecurityHeadersMiddleware`, pure ASGI),
  registered outermost in `main.py`. Sets `Strict-Transport-Security`,
  `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`,
  `Cross-Origin-Opener-Policy: same-origin`, and a strict `Content-Security-Policy`
  (`default-src 'none'; …`) on every response (errors included); the `/docs`,`/redoc` UIs are
  exempted from the CSP so they still render.
- **Verified:** unit tests (`tests/unit/shared/test_security_headers.py`) + **live** `curl -D-`
  on `/config` shows all six headers present.
- **Remaining:** strip the `server: uvicorn` banner at the reverse proxy (R-04/ops).

## Phase B — hardening

### R-06 · Client CSP + non-persistent token store (F-06) — **M**
- **Approach:** set `oidc-client-ts` `userStore` to `sessionStorage` (or in-memory); ship a
  strict CSP at the client's static edge (nginx/CDN) — `default-src 'self'`, no
  `unsafe-inline` where feasible, lock `connect-src` to the API+IdP origins; keep the 300s
  access-token TTL; for the highest assurance, evaluate a BFF/refresh-rotation pattern.
- **Accept:** tokens not in `localStorage`; CSP present and report-only-tested then enforced.

### R-07 · Validate `/users/{id}` (F-08) — **S**
- **Approach:** constrain the path param to a UUID (FastAPI `Path(pattern=...)` or an
  explicit check) before it reaches the Keycloak adapter.
- **Accept:** non-UUID id → `400` before any upstream call.

### R-08 · Catch-all 500 handler (F-10) — **S**
- **Approach:** register a handler for unhandled exceptions that returns the standard error
  envelope (generic message, no internals) and ensures CORS headers; keep tracebacks to logs
  only.
- **Accept:** an induced unexpected error returns the envelope `500` with CORS, no stack.

## Phase C — compliance & process

### R-09 · Secret rotation + management (F-07) — **S** (process)
- Rotate all dev credentials for non-dev; document that `realm-fdp-dev.json` and
  `compose.yaml` are **dev-only**.

### R-10 · PII-in-logs review (F-09) — **S**
- Define a logging policy: avoid `subject` on hot non-audit paths; set retention/access
  controls on logs that contain identifiers; consider hashing the subject in app logs
  (keep the identified trail in the audit graph/`AuditLog`).

### R-11 · Mirror `/users` mutations into the FDP audit log (F-11) — **M**
- Emit an audit event for create/update/delete/role-change in `identity/keycloak_admin.py`
  (or the router) so user-management actions appear in the unified FDP audit trail alongside
  the IdP's own log.

### R-12 · Dependency scanning + SBOM (F-12) — **S**
- Add `pip-audit`/`osv-scanner` and `npm audit` to CI; generate an SBOM; gate on
  high-severity advisories; keep RDFLib pinned ≥7 with a note referencing R-01/R-02.

## Suggested order & ownership

1. **R-01** (SSRF) and **R-05** (headers) — small, high value, server-team, this sprint.
2. **R-02** (rate limiting), **R-03/R-03b** (store gate + LOAD), **R-08** — server-team.
3. **R-04** (TLS/deploy), **R-09** — platform/ops.
4. **R-06** (client CSP/token store) — client-team.
5. **R-07, R-10, R-11, R-12** — hardening/compliance backlog.

## Out of scope (operator responsibilities to verify for HIPAA)

Encryption-at-rest and key management, backup/DR, log retention, a formal access-review
process, BAAs with hosting/IdP providers, and penetration testing by an accredited third
party before production go-live.
